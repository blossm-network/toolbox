# Command POST handler

Runs a command's `mainFn`, submits its events, awaits an optional `thenFn`, and
then assembles the HTTP response. Event submission can mean queue acceptance;
numbered events use the existing synchronous persistence path.

`thenFn` can return response contributions explicitly:

```js
return {
  events,
  response: { receipt },
  thenFn: async () => {
    const { body } = await commandFn({
      domain: "session",
      name: "upgrade",
      payload: upgrade,
    });

    return {
      response: { context: body.context },
      tokens: body._tokens,
    };
  },
};
```

| Callback field | Behavior                                                                 |
| -------------- | ------------------------------------------------------------------------ |
| `response`     | Shallow-merge keys with the main response; callback keys win collisions. |
| `headers`      | Shallow-merge keys with the main headers; callback keys win collisions.  |
| `tokens`       | Append to the main token array, preserving order and duplicates.         |
| `revoke`       | Append to the main revocation array, preserving order and duplicates.    |
| `statusCode`   | Override the main status when supplied, including status-only replies.   |

Nested response objects are replaced as complete values, not recursively merged.
Omitted or null fields leave the main values intact. Returning undefined or null
from the callback preserves the existing behavior, including an empty 204 reply.
Callbacks that already mutate the response object or token arrays still work.
When adopting returned arrays, stop appending those same values through mutation
or they will be included twice.

Other returned fields, including `events` and `thenFn`, are ignored. Submit any
additional events explicitly through the existing `logEventsFn` path. A callback
failure propagates before the success response is sent; it cannot undo events
already submitted.

The runtime still assembles `_tokens`, `_revoke`, `_id` and `_tx` under their
existing conditions after merging the application response. At the command
gateway, token cookies are set before revocations, so revocation retains priority
when both target the same cookie.

An explicit status without a response now reaches `sendStatus(statusCode)` rather
than being replaced by 204. Express supplies its usual reason text for those
statuses; 204 still has no body.

## Release and adoption

Release `@blossm/command-post`, update `@blossm/command` to depend on that release,
and release the command server before rebuilding generated commands that use
returned callback fields. The current `^0.0.308` dependency does not accept
`0.0.309`; publishing only the POST package will not update existing servers.
Existing deployed binaries must be rebuilt or redeployed to gain the contract.

## Event write outcomes

`thenFn` receives `{ outcomes }`, with one `{ event, status }` per event returned
by `mainFn`, in the original input order, even across stores. `event` is the
original application descriptor, not the persisted record; a root generated by
the framework is not added to it. `logEventsFn(events)` returns the same outcome
list for that explicit submission.

```js
return {
  events: [answerEvent],
  thenFn: async ({ outcomes }) => {
    if (outcomes[0].status !== "committed") return;
    return upgradeSession();
  },
};
```

| Status      | Meaning                                                                                              |
| ----------- | ---------------------------------------------------------------------------------------------------- |
| `committed` | This submission appended the event and its store transaction completed.                              |
| `duplicate` | The store skipped this event because its key was already present, or appeared earlier in this batch. |
| `queued`    | The queue accepted this submission; persistence has not been confirmed.                              |
| `unknown`   | An older store, RPC, or custom adapter supplied no per-event outcome.                                |

The runtime requests outcomes from `addFn` with `returnOutcomes: true`. The
updated generated adapter forwards that option to event-store RPC. HTTP success
alone never becomes `committed`; callbacks requiring a fresh append must check
that status explicitly. Empty submissions yield an empty list. Existing
zero-argument callbacks continue to work and still run after duplicate success.
Returning early skips only the callback's work: it does not remove response
values, tokens or effects already produced by `mainFn`.

Duplicate retries retain successful no-op behavior, including numbered events
already found by deduplication. Concurrent requests that both miss the duplicate
lookup can still encounter a number/unique-key conflict; those failures propagate
and do not invoke `thenFn`. A failure in one store cannot undo a sibling store's
commit. Publication can also fail after a commit and before its outcome reaches
the caller. A committed outcome does not mean projections have caught up.

Outcomes do not make callbacks durable. A crash after commitment can prevent the
callback from running, and a successful duplicate retry will report `duplicate`.
Essential follow-up work needs a persisted action written in the same transaction,
a retrying worker and receiver-side idempotency. The existing
[notification outbox proposal](https://github.com/blossm-network/toolbox/pull/133)
is the owner to reuse for that separate design; it does not currently persist
arbitrary `thenFn` callbacks or recover their HTTP/token response.

### Outcome rollout

Release the generic POST handler and rebuild the event-store servers with that
version. Release generic RPC and event-store RPC with updated dependency ranges,
and release command POST plus its command-server dependency range. Release and
rebuild the CLI-generated adapter with those clients/runtimes before adopting
outcome-sensitive callbacks. Package versions are unchanged in this proposal.
Older stores/adapters remain usable but produce `unknown`. Keep Dia's `answerId`
until the complete path is released, deployed and its callback checks commitment.
